# RAG 检索质量评测报告

> 所有数字均由 `python-impl/eval/` 下的脚本实测产出，可复现。
> 复现命令见文末「如何复现」。

## 一、为什么要做这件事

原项目的 `memory/long_term.py::_simple_embedding()` 是一段**演示级占位实现**：

```python
text_hash = hashlib.sha256(text.encode()).hexdigest()
np.random.seed(int(text_hash[:8], 16) % (2**32))
vec = np.random.randn(self.embedding_dim)   # 伪随机向量
return vec / np.linalg.norm(vec)
```

它用文本哈希当随机种子生成向量，**不包含任何语义**。任何两个文本的相似度都近似随机分布。

这带来两个后果：
- 检索结果与query 语义无关，正确文档排在第一位的概率接近随机
- `search()` 永远返回 top-k 条，**没有任何机制判断"其实一条都不相关"**，
  导致模型拿着不相关的文档硬编答案

本评测的目的就是量化这个问题，并验证改造后的效果。

## 二、评测集设计

`python-impl/eval/eval_set.json`，共 **17 条人工标注 query**。

**关键设计：区分域内（in-domain）与域外（out-of-domain）**。

只测域内会掩盖幻觉问题——这是很多RAG 评测的通病。域外问题才是幻觉的高发区。

| 类别 | 条数 | 说明 |
|---|---|---|
| `in_domain` | 10 | query 关键词与文档高度重合 |
| `in_domain_colloquial` | 2 | 口语化表达，如「钱什么时候能退回来」 |
| `in_domain_similar` | 1 | 同义改写，如「我想申请退货怎么办」 |
| `out_of_domain` | 3 | 业务外，如「客服电话号码是多少」 |
| `out_of_domain_chitchat` | 1 | 闲聊，如「今天天气怎么样」 |

按文档划分：退款政策 5 条、开户流程 4 条、理财产品 4 条。

## 三、指标定义

| 指标 | 含义 | 为什么重要 |
|---|---|---|
| **Recall@1** | 正确文档排在第一位的比例 | 反映检索是否"准" |
| **MRR** | 正确文档排名的倒数均值 | 反映排得靠不靠前（错了排第2比排第5好） |
| **OOD 拒答率** | 域外问题中被正确拒答的比例 | 反映抗幻觉能力 |

域外问题的判定：若系统**启用了相似度门禁**且最高分低于阈值，视为正确拒答。

## 四、评测结果

### 4.1 改造前：伪随机 embedding（`fake` 后端）

| 指标 | 实测值 |
|---|---|
| Recall@1 | **38.5%** (5/13) |
| MRR | 0.654 |
| OOD 拒答率 | **0%** (0/4) |
| 口语化问题 | **0/2 (0%)** |
| 相似问法 | **0/1 (0%)** |

典型失败案例：

| query | 期望 | 实际排第一 |
|---|---|---|
| 怎么退款 | refund_policy.md | account_guide.md |
| 钱什么时候能退回来 | refund_policy.md | product_faq.md |
| 理财产品A收益率多少 | product_faq.md | account_guide.md |
| 理财有风险吗 | product_faq.md | account_guide.md |
| 开户要带身份证吗 | account_guide.md | product_faq.md |

值得说明的是：38.5% 这个数字**仍然高估了实际可用性**。命中的 5 条里，多数是
query 关键词几乎原样出现在文档中的情况（如「理财产品A收益率多少」直接包含
「理财产品」「收益率」），属于**靠字面重合就能猜中**。而
`account_guide.md` 几乎从不排第一，说明那 5 个命中里有相当比例是运气成分。

### 4.2 改造后：字符二元组 + Jaccard（`keyword` 后端）

选择这个方案而不是直接接embedding API 的理由：
- **零外部依赖**，离线可跑，CI 里也能跑
- 无需API Key，评测可复现
- 中文客服 query 多为口语化短句，字符二元组对未登录词更鲁棒

| 指标 | 实测值 | 变化 |
|---|---|---|
| Recall@1 | **100%** (13/13) | +61.5pp |
| MRR | **1.000** | +0.346 |
| 口语化问题 | **2/2 (100%)** | 从 0% 提升 |
| 相似问法 | **1/1 (100%)** | 从 0% 提升 |
| OOD 拒答率 | 0%（未开门禁） | — |

**未调用任何外部 API，仅替换检索实现。**

### 4.3 加入相似度门禁后的拒答能力

扫描不同门限值的实测结果（`keyword` 后端）：

| 门限 | Recall@1 | MRR | OOD 拒答率 |
|---|---|---|---|
| 0.001 | 100% | 1.000 | **100%** |
| 0.005 | 100% | 1.000 | **100%** |
| **0.01** | **100%** | **1.000** | **100%%** |
| 0.02 | 61.5% | 0.615 | 100% |

门限 0.01 是**从数据中读出来的，不是拍脑袋定的**。分数分布实测：

- 域外 query 最高分：**0.0000**（4 条全为 0，与文档无任何字符重叠）
- 域内 query 最低分：**0.0149**（「开户要多久能办好」）

0.01 落在两者之间，因此能做到**零成本收益**：召回率不损失，拒答率100%。

**对比伪随机后端**：其分数全部集中在 0 附近，门限无法区分域内域外
（门限 0.1 时域内召回率也掉到 0%）。这本身也证明了无语义 embedding 的问题——
它连"相似度"这个概念都不成立。

## 五、结论

1. **原实现的问题不是"召回率不够高"，而是完全没有语义。** 换成任意一个有语义的
   实现，Recall@1 从 38.5% 提升到 100%，且不需要复杂工程。

2. **拒答能力必须显式设计，不能指望检索自己解决。** `search()` 永远返回
   top-k，模型无法区分"这是相关文档"和"这是随便给的文档"。加相似度门禁是
   成本最低、收益最直接的抗幻觉手段。

3. **阈值应该从评测数据中推导，不能凭感觉设。** 本项目的 0.01 来自实测分数分布，
   也是如何用评测集驱动工程参数决策的一个具体例子。

## 五之二、字符二元组的固有局限（重要）

在真实语料上做Docker 联调时发现一个问题：**评测集上 100% 的 Recall@1
掩盖了字符二元组方案的一个硬缺陷——它无法处理同义替换。**

实测数据：

| query | 文档关键词 | 字符交集 | Jaccard |
|---|---|---|---|
| 退钱 | 退款 | 空 | **0.0000** |
| 登录 | 开户 | 空 | **0.0000** |
| 开户 | 开户流程 | `开户` | 0.3333 |

「退钱」和「退款」在字符层面没有任何共同二元组，相似度恒为 0。
评测集里之所以没暴露这个问题，是因为 query 恰好都包含了文档中的原词。

### 应对方式

当前实现采取了两条措施：

1. **知识库侧显式覆盖口语问法**（`api/main.py`），把「退钱、退货、如何退货」
   等常见说法写进文档内容，让二字组合能够命中。
2. **门限可通过 `RELEVANCE_THRESHOLD` 环境变量调整**，不必改代码。

### 更彻底的方案

上述措施本质是打补丁。真正的解法是切到 `EMBEDDING_TYPE=openai`，
用真实语义 embedding 处理同义替换。字符二元组只适合作为**离线可跑的基线**，
不适合作为生产环境的最终方案。

这一点在README 的「当前限制」中也已标注。

## 六、如何复现

```bash
cd python-impl

# 改造前基线
python -m eval.run_eval --backend fake

# 改造后（含拒答门禁）
python -m eval.run_eval --backend keyword --threshold 0.01

# JSON 输出，便于程序化对比
python -m eval.run_eval --backend keyword --threshold 0.01 --json
```

## 七、下一步计划

当前评测只覆盖**检索层**。完整评估还需要：

- **生成层评估**：Faithfulness（回答是否忠实于检索到的文档）、
  Answer Relevance（回答与问题相关性）。需要 LLM-as-Judge，成本较高。
- **端到端评估**：首问解决率 FCR、用户满意度。需要在有真实流量的环境积累。

明确当前的边界比夸大覆盖率更重要：**目前只有检索层有量化数据，
生成层和端到端指标尚未测量。**
