# 面试问答稿 — 智能客服多Agent系统

> 使用方式：每题分「问题 / 怎么答 / 追问预案 / 边界」。
> 核心原则：**只说自己能指出代码支撑的东西**。答不上来就说"这块我没做"，比编数字安全得多。

---

## 一、项目定位（开场必问）

### Q：介绍一下你这个项目

**怎么答**（约 60 秒）：

> 这是一个基于 Supervisor 编排模式的多Agent 智能客服系统，参考 LangGraph 的图编排思路实现。
> 整体链路是：意图路由 → 知识检索 → 工单处理 → 合规审查 → 汇总回复。
> 我在这个项目上主要做了三件事：
> 一是**补齐了容错层**，所有Agent 节点统一做超时控制和降级；
> 二是**重写了检索层**，原实现的 embedding 是伪随机生成的，没有语义，我换成了可切换的真实实现并加了相似度门禁；
> 三是**建立了评测集**，用Recall@1、MRR、拒答率三个指标量化检索质量。

**追问预案**：
- "为什么选LangGraph 而不是 CrewAI？" → 图模型 vs 任务队列。关键是**所有回复必须过合规审查**这个硬约束，用图只需加一条统一边，用if-else 每个分支末尾都要加审查逻辑。
- "Supervisor 和if-else 路由区别？" → Supervisor 维护全局 state、支持条件分支/并行/检查点恢复，且每个节点自动生成 trace span。

## 二、RAG 与检索质量（最高频，也最能体现深度）

### Q：你的检索准确率怎么评估的？

**这是最关键的一题。原项目文档声称 92%，那个数字是编的。正确答法是用我自己的方法论。**

**怎么答**：

> 我评估分三层，这是业界通行的做法：
>
> **第一层是检索质量**——用 Recall@K 和 MRR。
> **第二层是生成质量**——用 Faithfulness（回答是否忠实于检索到的文档）和 Answer Relevance。
> **第三层是端到端**——FCR 和 CSAT。
>
> 我自己先做了第一层。建了一个 17 条query 的标注集，关键是**把域内和域外分开**：
> 域内 13 条，按query 和文档的关键词重合度分三档——直接重合、口语化表达、同义改写；
> 域外 4 条，专门测幻觉。
> 只测域内会掩盖幻觉问题，这是很多评测的通病。
>
> 实测结果是：**改造前Recall@1 只有 38.5%**，口语化问题是 0%。
> 我定位到根因是embedding 实现——原项目用 sha256 当随机种子生成伪随机向量，完全没有语义。
> 换成有语义的实现后，Recall@1 到 100%，MRR 从 0.654 到 1.0。
> 加入相似度门禁后，知识库外问题的拒答率从 0% 到 100%，而且召回率没有损失。

**追问预案**：
- "为什么不用真实embedding API，非要用字符二元组？" → 我同时实现了三个后端做对比。选字符二元组作为默认是因为它零外部依赖、离线可跑、CI 里也能跑；真实 embedding 需要 API Key，评测不便复现。生产环境会切到 OpenAI 兼容的 embedding。
- "38.5% 是不是高估了可用性？" → 是的。命中的 5 条里多数是query 关键词几乎原样出现在文档里的情况，靠字面重合就能猜中，属于运气成分。
- "阈���0.01 是怎么定的？" → **从数据里读出来的**。我扫了 0.001到 0.4 的一系列门限，发现域外query 最高分是 0.0000，域内最低分是 0.0149，0.01 落在两者之间，所以能零成本收益。工程参数应该由评测驱动，不是拍脑袋。
- "生成层评测为什么没做？" → Faithfulness 需要 LLM-as-Judge，成本较高。我判断当前阶段优先保证检索层，因为检索是链路上游，上游错了后面都对不了。端到端指标需要有真实流量才能积累，我没有伪造。

### Q：模型胡说八道怎么办？

**怎么答**：

> 分三层处理，我实现了前两层：
>
> **检索层做门禁。** 检索总会返回 top-k 条，哪怕全都不相关。所以我加了相似度阈值，最高分低于阈值就返回空结果，让上层明确知道"知识库没有相关信息"。实测域外拒答率从 0% 到 100%，而且召回率没损失。
>
> **Prompt 层约束。** 要求模型严格基于检索到的文档回答，文档里没有就说没有。
>
> **合规层兜底。** 规则引擎检查敏感词和 PII。
>
> 更彻底的方案是加一个"无依据"判定——如果检索结果不足以支撑回答，直接拒答转人工，而不是让模型自由发挥。这个我还没做完整。

### Q：为什么要做混合检索？

> 向量检索对专有名词、型号、编号这类精确匹配偏弱——"XR-770" 和 "XR-700" 的 embedding 距离很近。BM25 这类关键词检索能补上精确术语的短板。
> 融合用 RRF（Reciprocal Rank Fusion），按排名倒数加权，避免手工调 BM25 和向量的权重。
> 我目前只实现了字符二元组这一路，还没做 BM25 和向量的真正融合，这是下一步计划。

## 三、容错与降级（我们实际新增的能力）

### Q：如果某个 Agent 超时了怎么处理？

**原项目文档写了"三层防御"，但代码里搜 `wait_for` 是零命中。现在这是真实实现。**

**怎么答**：

> 我用 `asyncio.wait_for` 给每个 Agent 节点加了超时包装，默认 10秒。超时后不抛异常中断链路，而是返回带降级内容的 state。
>
> 降级话术是**按 Agent 职责区分**的，不是统一一句"系统繁忙"：
> - 知识检索超时 → "知识库查询超时，已为您记录"
> - 工单超时 → "工单提交中，请稍后查看"
> - 合规审查超时 → **按不通过处理**
>
> 最后这条是个 trade-off：合规审查超时按放行处理，风险是一句违规回复可能带来监管处罚；按不通过处理，代价只是用户多等几分钟。金融场景下这个不对称，所以宁可误拦。
>
> 另外还捕获了单个 Agent 抛出的普通异常，同样降级处理，避免一个节点失败拖垮整条链路。

**追问预案**：
- "降级率怎么监控？" → AgentExecutor 维护每次执行的耗时和降级标记，summary() 可以拿到总调用数、降级次数、降级率和分 Agent 统计。这块我还没接到 /api/metrics 暴露出去。
- "为什么是 10 秒？" → 参考 LLM API 的 p99 延迟。实测 DeepSeek 单次调用 1-3 秒，10 秒是留了余量。这个值应该按实际 p99 调整，我还没做压测校准。
- "有没有重试？" → 目前没有。设计上不打算给副作用类操作自动重试（避免重复创建工单），只读操作可以考虑指数退避重试，但还没实现。

### Q：怎么保证一个节点失败不会拖垮整条链路？

> LangGraph 本身没有超时机制，原实现里任何一次 LLM 调用挂住都会让整个请求一直阻塞，用户侧表现为"转圈不动"。
> 我的做法是把所有业务节点统一包一层 AgentExecutor，超时和异常都转成降级 state，链路继续往下走。
> 同时降级会记 `retry_count`，后续可以扩展成"降级次数超N 次才转人工"。

## 四、架构设计

### Q：多轮对话的上下文丢失怎么解决？

**这里必须诚实：原项目的三层记忆实际是半成品。**

**怎么答**：

> 原项目设计了分层记忆：工作记忆（进程内）、短期记忆（Redis）、长期记忆（向量库）。**但我核查后发现短期记忆实际上没生效**——它被传进图里，可是没有任何节点调用 `get_context_window()`，只写不读。多轮上下文是靠 LangGraph 的 Checkpoint 兜的。
>
> 我认为这个设计思路是对的，职责划分清晰：工作记忆放当前推理状态、短期记忆放会话上下文、长期记忆放知识。
> 真正要做的是把读写接上，并且用 token 预算而不是固定条数来截断——固定条数在长对话里会静默丢掉早期关键信息，token 预算更贴合模型的真实约束。
> 这块我还没完成。

**追问预案**：
- "Checkpoint 和短期记忆有什么区别？" → Checkpoint 是 LangGraph 状态层面的持久化（进程内 MemorySaver），短期记忆是业务层面的会话缓存（Redis，可跨实例、可设 TTL）。两者粒度不同，可以共存。
- "为什么短期记忆要放 Redis？" → 支持多实例部署共享会话状态，以及 TTL 自动过期。生产环境不用 MemorySaver 是因为它是进程内的，多副本会丢。

### Q：意图识别是怎么做的？

**这里有个坑要说清楚，因为原代码有 bug，我修了。**

**怎么答**：

> 原来这个项目有个问题：`IntentRouterAgent` 被实例化了但从未挂到图上，意图识别实际上就是Supervisor 里一句 prompt 让 LLM 直接返回节点名，属于字符串匹配式路由。
>
> 我把 IntentRouter 真正挂成了图的入口节点，先做意图分类再路由，同时保留 Supervisor 做兜底决策。意图分类会返回意图、置信度和关键实体。
>
> 置信度可以用来做低置信度自动转人工——这个我还没接。

## 五、评测与工程实践

### Q：你怎么保证改动没引入回归？

**怎么答**：

> 我补了单元测试，重点覆盖三个新增的逻辑：
> 超时降级是否触发、合规超时是否正确拦截、异常是否不破坏链路；summarize 聚合时dict 类型是否会抛异常；意图归一化在 LLM 输出带标点时是否还能正确识别。
>
> 一共 10 个测试，全部通过。这里有个细节：executor 模块我做成了不硬依赖 langchain，这样测试不用拉整条 LLM 依赖链，可以单独跑。

### Q：项目里还有什么不足？

**这题必须答，而且答好是加分项。**：

> 我能明确说清三个：
>
> **一是评测只覆盖了检索层。** 生成层的 Faithfulness 和端到端的 FCR 都没有测，前者需要 LLM-as-Judge，后者需要真实流量。这是目前最大的缺口。
>
> **二是短期记忆没接通。** 原设计的 Redis 那一层只写不读，多轮上下文实际靠 Checkpoint。
>
> **三是混合检索没做。** 现在只有字符二元组一路，BM25 和向量的 RRF 融合还没实现，精确术语匹配能力偏弱。
>
> 另外工期原因，我只跑了 Python 版，Java 和 Go 那两套没有验证过。
